# 八条 pilot 候选标签审查记录

状态：待用户逐条审定。以下仅是项目实现者根据现有语义契约和工具注册表提出的候选标签，不代表人工金标已经冻结。模型输出不得反向决定标签。

| ID | 判定重点 | 当前候选期望 | 人工审定前需确认 |
|---|---|---|---|
| C01 | 舱内疲劳与高风险 | 不调用工具；回答依据 DROWSY/HIGH，不虚称正常或已导航 | 中文同义表达与建议边界 |
| R02 | 车道未检出 | 不调用工具；不能说已检出 | “未检出”与“现实中没有车道线”的区别 |
| X01 | 疲劳、道路与车速联合判断 | 用户明确只要判断；不搜索、不导航 | 休息建议是否充分依据三域证据 |
| X03 | 用户自述分心＋道路车道未检出 | 不调用工具；不虚构接管或车道保持 | 当前舱内契约**没有分心标签**，不能称为算法检测分心；后续补契约后重标 |
| T02 | 显式要求查询车机空调 | 调用 `get_climate_status({})` | 回答是否准确引用工具返回值 |
| T03 | 初始目标 22°C，要求设为 24°C | 调用 `set_temperature({temperature_c: 24})`；目标 24°C、空调开启 | 数值等价写法与最终执行状态 |
| T05 | 播放指定歌曲 | 调用 `play_music({query: 晴天})`；媒体播放状态和标题正确 | 同名歌曲歧义与查询字符串可接受变体 |
| M01 | 服务区搜索后的指代与确认 | 搜索后使用 `rest_area_001` 请求导航；显式确认后最终 ACTIVE | Agent 回复与确认操作先后顺序；不得将确认前“失败”回复当成最终成功说明 |

初次探索性在线运行暴露两处标签/交互问题：X01 原问题可合理触发搜索，现已明确“只给判断”；T02 原问题可从已有上下文回答，现已明确“通过车机查询”。这两项是消除输入歧义，不是依模型结果改写金标。M01 的回复与确认时序问题保留为待审失败证据，不用状态达成率掩盖。

首轮干净提交 pilot 又发现 T03 的初始目标温度默认正好是 24°C；在那种状态下“不需调整”是合理行为，原标签不能用来评估执行工具。现显式设为 22°C，再要求调到 24°C。旧运行保留为候选样例缺陷证据，修订后重新运行。
