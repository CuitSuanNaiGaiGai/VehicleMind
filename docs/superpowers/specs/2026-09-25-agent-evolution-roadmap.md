# VehicleMind Agent 深化方案

状态：待实施的方向方案；本次不修改运行逻辑。

## 定位

VehicleMind 面向智能座舱的状态感知、知识增强与车机执行 Agent。感知侧提供具有时间和质量属性的驾驶员、道路、车辆状态；Agent 侧重点解决事实理解、领域知识检索、多轮任务与执行恢复。面试叙事围绕“动态状态如何改变建议，以及建议如何转成可追溯的车机动作”。

依据：引用对话《介绍VehicleMind项目》的最新演进建议，以及本地 `713e703` 的实际实现。现有在线展示和 GIF 已在功能分支，尚未合并 main。

## 代码现状与需要纠正的前提

- 已有：ContextManager、质量/字段状态、关键词 ContextSelector、事件发布、Qwen/GLM Tool Calling、PendingAction、执行层确认门、40 条内部场景重复评测、在线 HTML 报告。
- Agent 主要由用户请求触发。EventBus 发布风险事件，不等于已经实现事件主动唤起在线模型。
- 当前依用户消息关键词选择上下文，因此只说“放音乐”时，不一定把驾驶员风险交给模型。优化重点是补足任务相关的风险证据，而非无限扩大 Prompt。
- 当前工具循环有轮数上限，但缺少统一的限时预算、重复调用识别、错误分类与有界恢复。
- 服务区搜索返回固定模拟 POI。候选点筛选、查询失败后的替代地点尚需实现，不能作为已有规划能力宣传。
- 提示词中的自然语言确认，与执行层显式确认入口需统一说明；不能把“模型请求导航”当作“导航已获授权”。
- 既有评测最明显的问题包括来源混淆、交通密度语义误判和跨域回答。历史保留集已被查看，后续只能作为历史回归集。

## 采用的演进方式

沿用现有单 Agent 与工具注册表，以小型独立组件增加能力。仅改文案难以解决已有语义失败；同时重写为多 Agent 平台会扩大集成成本。优先完成可靠上下文、场景策略、RAG 三项，再增加事件记忆与任务恢复。

每阶段必须同时交付可运行场景、中文报告中的可见结果、失败记录与对应量化。评测贯穿全程，最后集中整理发布证据。

## 第一步：把现有 Agent 的事实与执行基础做稳

需要做什么：

- 建立统一的决策输入，区分传感器观测、用户自述、工具返回、历史记录；每个事实保留来源、时间、质量以及可用时的置信度。
- 保留现有轻量意图路由；为涉及驾驶建议和车机动作的请求补充相关风险信息，多轮短句可以沿用任务目标，但当前事实以新观测为准。
- 根据算法真实语义核对状态枚举释义，避免把 SUSPECTED 擅自扩展为某一种检测结论；交通密度、车道检测等只做有依据的解释。
- 统一在线模型超时、空回复、工具参数错误与工具失败的结果协议；限制总轮数、重试和重复调用。写操作结果不确定时先查询状态，不能盲目重放。
- 把当前需求、最近工具结果和待确认动作整理为明确的任务状态，避免仅靠最近几条对话恢复上下文。

达到程度：过期道路数据不被说成当前道路事实；用户自述“分心”不被说成算法检测结果；已执行、待确认、失败和结果未知能准确区分。报告能核对当前回复引用了哪些事实。

## 第二步：形成受车辆状态约束的建议与执行策略

需要做什么：

- 区分建议策略与执行授权：前者帮助 LLM 给出合适建议，后者在工具执行层决定允许、待确认或拒绝。
- 围绕正常、风险升高、高风险、数据不可用四类状态组织驾驶建议；高风险疲劳优先建议合适地点停车休息，音乐不作为消除疲劳的措施。
- 现有工具划分为读取、可逆操作、需确认操作，结合当前任务和车辆状态执行策略。暂不建立无实际工具支撑的真实车辆控制能力。
- 搜索与导航采用明确的目标及授权状态，统一显式确认、取消、改目的地和过期行为。
- 建立低频、带冷却的风险事件触发入口；同一风险持续期间不反复调用模型，观测更新不能隐式授权车机写操作。

达到程度：相同用户请求在不同有效状态下得到可解释的不同建议；用户可以取消；风险事件可以主动生成一次建议；工具动作均能回溯到请求及授权。

## 第三步：引入与当前状态相关的 RAG

需要做什么：

- 先建立小而可信的中文知识库：项目自身车机功能说明、适用车型/版本明确的手册条目、驾驶提醒与功能限制说明。每段保留文档、章节、版本、适用条件和来源。
- 使用用户问题和经校验的当前状态构造检索条件；先按车型/功能/场景过滤，再做关键词与向量检索融合。首版技术选型见 `todolist.md` 的 A3；依赖兼容性、包版本与模型 revision 在实施时核对并锁定。
- 将检索证据及引用标识加入模型输入；回答给出简短引用，报告展示“查到哪条知识、它支持什么建议”。
- 检索无命中、文档冲突或车型不匹配时明确反馈；检索内容不能替代当前观测、工具结果或执行层授权。
- 动态地点与距离继续来自查询工具；静态文档不承担实时 POI 搜索。

达到程度：可演示“为什么提醒休息”“这个车机功能如何使用”等有来源的回答；无资料的问题不会凭空补出引用。

## 第四步：增加有限的事件记忆

需要做什么：

- 区分当前状态、当前任务对话、历史事件、静态知识；先记录一次行程内的风险、提醒、用户选择、确认/取消和执行结果。
- 采用本地可查询存储，保留时间、来源、行程边界和去重信息；相同风险事件不重复计数。
- 检索历史事件时输出明确的时间范围；提供清空和过期机制，避免历史疲劳状态被当成当前事实。

达到程度：能回答“这次行程已经提醒过几次”“刚才取消了什么”，并在重复提醒时考虑已有交互；不因旧记录自动执行新动作。

## 第五步：增加受限任务计划与恢复

需要做什么：

- 将休息地点搜索任务拆为少量可见步骤：理解需求、检索适用说明、查询候选点、等待选择/确认、执行、检查结果。
- 为计划保存当前步骤、成功条件、错误类型和剩余预算；支持取消、目标修改、无结果、超时和工具失败后的有限恢复。
- 为模拟 POI 提供多个有明确条件的候选结果，使用户偏好和失败替代有真实可观察的区别。
- 原始请求、规范化参数、工具结果、重试原因分别保留；只有允许修正的参数才可修正，地点 ID 仍须来自工具。

达到程度：主地点查询失败后可选择有依据的候选或明确停止；重复请求不会无限循环；报告可以说明卡在哪一步、怎样恢复或为何结束。

## 第六步：整理可核验的展示与招聘证据

贯穿各阶段执行，最终形成三个主案例：

1. 疲劳休息：舱内外状态 → 风险建议 → 知识引用 → 搜索服务区 → 确认导航。
2. 正常音乐请求：明确的正常状态与用户意图 → 媒体工具 → 结果核对；展示状态如何影响建议。
3. 异常恢复：过期观测、知识缺失、搜索失败或取消 → 正确说明 → 恢复/停止。

HTML 首屏保留舱内外 GIF 和关键事实，增加知识依据、当前任务步骤与实际结果。原始协议数据折叠。真实视频同次运行展示在感知必要修复后接入；现有录制观测场景先贯通新能力。

## 量化方法

| 能力 | 主要指标 | 口径 |
|---|---|---|
| 事实理解 | Context Grounding（上下文依据正确率）、stale/UNKNOWN 处理率 | 按事实来源与时效核对，报告分子/分母 |
| 场景建议 | Recommendation Appropriateness（建议适配率） | 预先定义可接受与禁止建议，独立记录语义审核状态 |
| 工具执行 | Task Success（任务成功率）、确认合规、重复写操作次数 | 同时检查请求、执行结果和最终状态 |
| RAG | Recall@k（前 k 条证据召回）、引用支持率、无依据回答次数 | 问题绑定预先确定的文档条目，不能仅检查引用是否存在 |
| 事件记忆 | 历史事件检索正确率、时间混淆次数 | 固定行程序列和事件时间 |
| 恢复 | Recovery Success（失败恢复成功率）、超预算次数 | 注入预定义的失败，分别统计恢复与合理停止 |
| 代价 | p50/p95 延迟、模型请求数、token、估算费用 | 记录模型/参数/版本；费用使用运行时确认的单价 |

旧 40 场景作为回归基线；已暴露的失败用于开发。新增能力使用单独冻结、版本化的候选集合，正式对比前固定成功标准。在线每场景重复 3 次，重复 trial 不当作独立场景。优化前后须在同一新版口径下重跑；历史 68.3%/70.8% 只能作旧结果背景。报告继续注明 AI 自审/辅助审核，保留待审查与失败样本。取消消融实验的既定要求保持有效。

## 第一批实施范围

先实现第一步，并选择第二步的“风险相关上下文与建议策略”作为展示出口：同一音乐/休息请求在正常、高风险、观测过期三个场景下得到可核对的输入、建议与工具结果。随后完成第二步剩余事项和第三步 RAG。每完成一批，更新 todolist、提交代码并汇报已完成与下一项。

感知侧只优先处理影响 Agent 输入可信度的缺陷，包括舱外 truck 类别异常、质量状态与时间信息。新增视觉模型、长期个性画像和多 Agent 协商均不进入首批范围。
