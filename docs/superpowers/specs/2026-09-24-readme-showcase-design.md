# VehicleMind GitHub 首页展示改版设计

## 目标与参考边界

参考用户提供的 PaperBase README 首页信息层级与排版节奏：居中标题、技术标签、锚点导航、演示图、能力表、架构图、结果、快速开始、设计决策与限制。只借鉴格式，不复制文案、指标、技术栈或许可表述。VehicleMind 的首页必须在约 30 秒内让招聘者看懂“舱内外感知 + Agent 编排 + 模拟车机”的核心价值，并能继续查看证据或运行 Demo。

## 首页内容顺序

1. 居中的项目名、中文一句话定位、少量真实技术标签与锚点导航。标签只列仓库实际依赖或已接入的技术：Python 3.13、OpenCV、MediaPipe、ONNX Runtime、YOLOPv2 路径、Qwen/GLM API、pytest 等；区分核心依赖与可选感知依赖。
2. “项目简介”用两段说明场景、核心链路和项目定位。明确是离线视频/录制观测驱动的原型，不是量产车机或自动驾驶系统。
3. “演示效果”直接显示现有舱内、舱外 GIF；另从一次干净、确定性离线回放生成报告页面截图，展示协同链路。三类图各有说明，不把已有 GIF 说成同一次回放的产物。
4. “核心能力”用紧凑表格列感知、统一上下文、事件、Agent、确认门禁、模拟工具和可复现报告；每项链接到已有模块或文档，不承诺未实现的能力。
5. “系统架构”用一个 GitHub 可渲染的 Mermaid 图，说明舱内/舱外语义观测、Context Manager、事件、Agent、用户确认、ToolRegistry 和报告的关系。图例说明录制观测路径与真实视频推理路径的差别。
6. “技术栈与个人工作”区分自编排代码、集成/适配代码、预训练模型和第三方依赖；重点解释 Agent 编排设计与可复现展示的工程贡献。
7. “结果与证据”只展示已有可核对证据：离线 Demo 断言、真实双模型 8 条候选 pilot 的运行事实、M01 确认流程修复前后单例对比，并链接技术报告。`needs_review`、17 条候选案例和本地未提交的原始 trace 不写成正式可靠性成功率。尚缺感知小样本指标与正式 Agent 成绩时不放空白/虚构数字。
8. “快速开始”保留现有无密钥离线 Demo 命令，区分可选真实视频运行、在线 Agent 评估和测试；在线命令必须说明需要自备 API Key。
9. 页面后半保留项目结构、关键设计决策、当前限制、Roadmap 与许可证，长说明优先链接到已有文档；不把未完成计划放在首屏主视觉。

## 资源与实现边界

- 主要改动为根目录 `README.md` 和用于展示的仓库内静态图片；不新建 Web 应用，不修改 Agent/感知算法行为。
- 报告截图从仓库当前离线场景生成，截图内不含本机绝对路径、密钥或用户数据；如生成受环境限制，则首页先使用现有 GIF，并在提交说明中明确缺口，不使用合成“运行截图”。
- GIF 继续直接嵌入首页，保证 GitHub 页面可见；Mermaid 采用 GitHub 支持的 Markdown 语法。所有展示文案中文，命令、协议和技术名保持原样。
- 当前分支未形成用户审定的 40 条金标或正式可靠性分数。首页不得借鉴 PaperBase 的数字或暗示与其评测规模相同。

## 验收

- 首页首屏能看到项目定位、真实技术标签和可点击导航；向下即可看到演示素材与协同链路。
- 图片路径和文档链接在仓库内有效；快速开始命令在干净提交上生成中文报告。
- README 中每一项能力或数字都有代码、资产、测试或报告可追溯；候选/正式、录制观测/真实推理明确区分。
- 运行全量测试、README 链接/资源检查和 `git diff --check`；完成后更新 `todolist.md` 中对应展示项，但“真实指标齐全”的最终首屏目标仍保持未完成。
