# B1：业务状态与多轮对话设计

日期：2026-09-27。状态：优先级已获用户认可；本文件为待审阅设计，尚未实现。

## 1. 目标与范围

将 VehicleMind 的发展主线收敛到 Agent 工程：先让一个业务任务跨多轮保持一致，再深化上下文预算、记忆和知识检索。车载场景是业务载体，不新增自动驾驶规划控制，不宣称端侧离线 LLM 能力。

本阶段交付一个可演示的休息地点会话：提出目标 → 补充条件 → 展示候选 → 询问候选 → 插入状态问答 → 返回任务 → 选择 → 显式确认或取消。原有模拟工具、确认门与有限恢复流程继续复用。

不纳入本阶段：长期偏好、对话摘要、跨进程恢复、多个并行业务任务、设施和途经点查询、真实地图、流式语音、端侧模型、RAG 重排序。上述能力不通过扩展提示词假装存在。

## 2. 现状与设计依据

核查基线为 `07c880b`，只读核查以下模块：

- `modules/vehicle_ai/agent/vehicle_agent.py`：持有 history/task/pending/trace，`chat()` 同时负责任务延续判断、取消、上下文组装和执行入口。
- `modules/vehicle_ai/agent/session.py`：历史只保存用户/助手消息并截取最近 12 条；另从近期 trace 选取历史证据。这不等于结构化业务状态或对话摘要。
- `modules/vehicle_ai/agent/task_state.py`：已有任务 ID、生命周期、待确认动作快照、工具结果及计划。
- `modules/vehicle_ai/agent/plan.py`、`plan_flow.py`：已有最多 9 步、1 次恢复的计划与候选，不再另建平行计划器。
- `modules/vehicle_ai/agent/pending_intent.py`、`target_resolution.py`：有限关键词分类、候选规范名称/别名匹配，不支持完整的多轮省略与条件合并。
- `modules/vehicle_ai/tools/navigation.py`：模拟搜索只支持 `max_distance_km` 与 `preferred_area`；后者是名称/别名子串过滤，不是真正地理区域理解。

因此本阶段不重复实现“工具调用”和“记忆存储”，而是补任务延续语义、条件更新、候选版本和只读插入问答边界。

## 3. 架构选择

选用“显式业务状态 + 确定性状态迁移 + 受限 LLM 意图解释”。

另外两种方案不采用：仅靠历史消息与提示词，难以保证条件与授权一致；整体迁移到新的 Agent 框架，会扩大改动面，且不直接解决业务状态问题。继续使用 Python dataclass/Enum、现有 JSON Schema 校验、Qwen/GLM 适配器、pytest 与中文 HTML。

拟定职责边界（路径为新增或调整目标，不表示已有实现）：

| 模块 | 单一职责 | 明确不负责 |
|---|---|---|
| `agent/dialogue_state.py` | 会话 ID、轮次、业务约束及其来源、待澄清项 | 调用模型、工具或保存授权 |
| `agent/dialogue_interpreter.py` | 将本轮话语解释为有 schema 的意图提议，执行有限确定性快速路径 | 修改任务、执行工具 |
| `agent/dialogue_reducer.py` | 校验提议并产生任务更新和允许的操作类别 | 网络调用、生成最终答案 |
| `agent/dialogue_coordinator.py` | 在现有 Agent 入口衔接解释、状态提交、只读问答和业务执行 | 实现第二套导航计划或工具注册器 |
| 现有 `task_state.py` / `plan.py` | 任务生命周期及候选事实的唯一来源 | 通过模型回复推断执行成功 |
| 现有 `turn.py` / `ToolRegistry` / 确认控制器 | 执行预算、工具校验、一次性确认与结果核验 | 信任意图解释结果作为授权 |

`VehicleAgent.chat()` 保留兼容入口，将新增会话分支委托给 coordinator。模块按职责拆分；新增生产模块原则上不超过 300 行，超过时先审查职责，禁止为满足行数机械拆文件。此次不做无关目录整理。

## 4. 状态与数据契约

### 4.1 一个会话，一个活动业务任务

- `session_id`：新建 Agent 或 reset 时生成；同一会话内不变。`turn_id` 单调递增。
- `AgentTask.task_id`：业务续接、条件修改、插入问答时保持；任务终止后明确开启新任务才更换。
- 已有 `TaskStatus` 保持为生命周期唯一来源，不增加一套含义重复的 dialogue status。
- 新业务字段挂接到当前任务：`revision`、`constraints`、`unresolved_constraints`、`clarification`、`last_presented_candidate_set_id`。
- 每个已接受条件保留 value、source_turn_id 与本轮原文片段。模型推测、历史助手回复不能作为用户新条件。

支持的条件仅为正且有限的 `max_distance_km`、名称/别名过滤 `preferred_area`。未给条件时沿用工具默认查询，不强迫用户填满表单。省略字段表示保留；明确移除条件用单独的 REMOVE 操作，不能把缺字段误当清空。明确新值覆盖同一字段旧值；同一句相互矛盾则澄清，不任选一个。

“有厕所”“沿途”“绕行不超过十分钟”保存为未解决条件并说明工具不支持，询问是否按已支持条件继续；用户没有明确放弃前，不宣称已找到符合全部要求的候选，不创建导航待确认动作。

### 4.2 候选事实只保存一份

继续以 `TaskPlan.candidates` 保存实际工具候选；扩展同属计划的候选快照元数据：`candidate_set_id`、`constraint_revision`、`created_at`、`presented_turn_id`、`expires_at`。会话只引用快照 ID，不另存可变候选副本。

- 序号来自系统实际展示的列表顺序，不允许模型重排后仍沿用旧序号；展示时保存序号到 canonical POI ID 的映射。
- 默认候选有效期 120 秒，使用现有可注入 action clock，与视频时间戳分开；待确认动作有效期不得晚于候选快照有效期。
- 条件变化后，旧候选、选择与待确认动作立即失效。新搜索失败也不恢复旧候选执行资格。
- 候选过期、序号越界、没有展示记录时，“第二个”必须触发重新查询或澄清，不能回退猜测名称。
- “换一个”有多个可能对象时询问用户；不默认第二个就是用户想要的对象。

### 4.3 生命周期与预算

业务任务等待用户补充或选择时为 `AWAITING_INPUT`；只读回答完成不能让活动业务任务被 `finish()` 标成 `COMPLETED`。业务生命周期与单次问答是否成功分别记录。

条件修改保持业务 task ID，但结束旧执行计划并生成新计划 revision；新候选必须重新产生，旧授权必须撤销。最多允许每个业务任务 3 次显式条件/目标修订，超过时进入 `AWAITING_INPUT` 并要求开启新任务，不能无限重建计划绕过预算。每个计划仍保持最多 9 步、1 次恢复；只读插入问答不消耗业务计划步数，但消耗本轮模型/工具预算。

用户明确取消后任务终止、候选选择不可再执行、待确认失效。“继续”不能自动复活取消、完成、失败的任务或恢复授权；需明确新请求。取消待办任务不等于取消已经运行的导航，后者仍走已有工具策略。

## 5. 话语解释与执行边界

解释输出使用固定枚举：`START`、`UPDATE_CONSTRAINTS`、`SELECT`、`ASK_CANDIDATE`、`SIDE_QUESTION`、`RESUME`、`CANCEL`、`UNCLEAR`。输出包括条件修改列表、候选指代、原文证据与澄清原因；不接受模型给出的 task ID、POI ID、授权或自由工具名。

处理顺序：

1. UI 的 `confirm_pending(action_id)` / `reject_pending(action_id)` 保持确定性，不经过 LLM 解释。
2. 独立且明确的“取消”“继续”和规范序号语句走有限规则快速路径；复杂、混合或条件式句子不使用子串直接取消。
3. 其余已进入业务会话的表达，通过现有模型适配器进行一次无业务工具的 JSON 解释。只传本轮文本、结构化任务摘要与候选展示映射，不传整个 trace。
4. schema、数值范围、候选指代及原文出处校验后才提交 reducer。无效 JSON、多个互斥意图或无法核实条件时澄清，原业务状态保持不变，过期失效仍正常执行。

LLM 解释最多请求一次，超时上限 15 秒并取本轮剩余时间的较小值；不做隐藏的修复循环。解释调用与后续回答共用 90 秒、5 次模型轮次和 10 次工具调用预算，不能为解释器重新启动完整预算。模型用量、耗时及失败单独记入 trace。

字段存在原文出处只证明来源可追溯，不证明模型理解必然正确；距离单位、序号与字段值需要确定性规范化和一致性检查，剩余语义错误通过在线评测暴露。

“好”“可以”“就去第二个”最多完成候选选择并产生待确认动作，不自动调用确认接口。诸如“如果找不到就取消”不能被误当成无条件取消；本期不支持的复合控制语句进入澄清，不扩展成自由代码执行。

## 6. 插入问答及恢复

`ASK_CANDIDATE` 从当前有效候选读取距离/名称/预计时间，不能凭模型常识补设施信息。`SIDE_QUESTION` 可调用现有只读上下文、知识和历史查询工具；执行层使用明确只读允许集合，即使模型请求写工具也拒绝。

插入问答不改变业务 task ID、constraints、选中候选和待确认动作的身份，不延长过期时间；状态快照只用于检查不变性，不在回答结束后恢复旧 pending，从而避免把已过期或撤销的授权恢复出来。

只读问答出错时说明本次问答失败，保留原业务进度。恢复任务时重新校验候选时效与版本；过期则重新查询，不能用历史摘要填充当前事实。主动风险建议仍沿用现有独立入口，不进入用户业务计划。

首版按同步单会话顺序执行；不宣称支持并发请求或执行中异步打断。两个 Agent 实例的 task/candidate/pending/history 必须隔离，不使用全局可变会话状态。

## 7. 兼容与展示

- B1 通过新增、默认关闭的配置开关启用；旧 40 场景入口继续使用原模式，不暗改历史评测行为。新演示入口显式开启并在报告标记模式。
- JSON 协议使用英文键名，中文报告用自然语言展示当前目标、已确认条件、未解决条件、候选顺序、待确认操作和每轮变化原因。
- 新 trace 记录 session/turn/task ID、task revision、意图提议及其验证结果、状态 diff、候选集版本、工具结果与模型调用预算；不保存或展示隐藏思维链。
- 报告主区只显示关键事实与业务步骤，原始 JSON 折叠；沿用既有 GIF 展示，不将 GIF 当作同次视频感知证据。
- 更新本阶段中文自测入口与 README 技术说明；新能力通过验证后再修改“已实现”陈述。

## 8. 验收矩阵

以下是验收目标，不是当前结果。固定使用模拟 POI；自动生成的句式和 AI 审核不称人工金标。

| 编号 | 场景 | 必须满足 |
|---|---|---|
| D01 | 查询后补充“十五公里以内” | task ID 保持，记录用户条件来源，新搜索参数一致 |
| D02 | 将十五公里改为十公里 | 新 revision，旧候选和 pending 失效，无旧授权执行 |
| D03 | 明确取消距离限制 | REMOVE 生效，未提及的其他条件保持 |
| D04 | 请求厕所或绕行条件 | 说明不支持并澄清，不能默默忽略后宣称满足 |
| D05 | 问“第二个多远” | 对应最后实际展示的第二个 POI，只读无导航动作 |
| D06 | 插入疲劳依据问答后返回 | 原 task/条件保持；观察质量依旧检查，不复活过期候选 |
| D07 | “就去第二个”后显式确认 | 新 pending 绑定当前 POI；确认前零导航写入，确认后仅一次 |
| D08 | 多候选时说“换一个” | 目标不明确时澄清，不随机选择 |
| D09 | 过期后说“继续”或引用旧序号 | 重新查询或澄清，旧 pending 无效 |
| D10 | 取消后说“好” | 不恢复任务或导航授权 |
| D11 | 条件修改后搜索失败 | 新条件保留并说明失败，旧候选不得重新用于执行 |
| D12 | 解释器超时、无效 JSON、冲突条件 | 有限结束且不误写业务状态，错误可追溯 |
| D13 | 插入问答时模型恶意请求写工具 | 执行层拒绝，原业务状态保持，写入次数为 0 |
| D14 | 两个会话交替运行 | 无候选、条件、授权和历史串话 |
| D15 | 对话超过旧 12 条窗口 | 早期业务条件仍由结构化状态保留，不依赖旧消息仍在 prompt |
| D16 | 超过修订或单轮调用预算 | 明确停止/等待输入，不能重建计划无限续费 |

确定性测试检查上述状态、参数、写入次数和时间边界，目标全部通过。在线测试冻结 16 条对应会话，每模型各重复 3 次，分别报告：Task Success Rate（多轮任务成功率）、State Consistency（应保持/更新的状态检查通过率）、Clarification Correctness（应澄清轮次正确处理率），并披露延迟、tokens、失败和审核错误。16 条是独立场景数，重复运行不增加独立样本量；不与旧 40 场景分母混合，不事后改题抬高分数。

## 9. 实施分段与审阅检查
