# VehicleMind 在线 Agent Golden Set 与评估框架设计

## 目标与优先级

下一阶段先搭建“舱内/舱外语义观测 → 统一上下文 → 在线 Agent 决策 → 车机工具 → 最终状态 → 评估报告”的完整闭环。暂不把新增安全规则、Prompt Injection 或感知算法精度作为本阶段主线；现有工具确认门禁保持不变。感知算法的小样本评测继续独立进行，不能把录制语义观测的 Agent 结果当作感知精度。

当前仓库只有一条带脚本化模型回复的完整回放场景。它适合验证编排和结果展示，但不能证明在线模型自主决策的成功率。在线评估必须让真实 Qwen、GLM 客户端产生工具选择、参数和自然语言回复，脚本化回放结果单独标为系统回归。

## 模型与配置

- 评估器每次运行显式指定 `qwen` 或 `glm`，不依赖 `.env` 中的 `VEHICLEMIND_LLM_PROVIDER`。该变量若在同一文件重复，后一个赋值通常覆盖前一个；已有进程环境变量还可能优先于 `.env`。两个 API Key 可共存，但不得写入代码、结果文件、异常消息或报告。
- 首版请求的模型标识分别为用户当前配置的 `qwen3.8-max` 与 `glm-5.1`。执行前对每家做一次真实 API 与工具调用预检，记录请求模型、响应模型标识（若返回）、端点主机、运行时间和客户端版本。预检失败不伪造结果，也不静默替换模型。Qwen 官方文档列出该模型 ID 和 Function Calling；智谱平台列有 GLM-5.1，但本项目账号与具体端点可用性必须通过预检确认：[Qwen 模型说明](https://help.aliyun.com/zh/model-studio/qwen3-8-max)、[智谱平台说明](https://www.bigmodel.cn/glm-coding?closedialog=true&ic=UMYTQHW8I2)。
- 当前 `QwenClient` 和 `GLMClient` 将温度固定为 `0.2`，`LLMResponse` 不含 usage。评估适配层应把温度、单次请求超时、最大工具轮次和有限重试固定为运行配置；有 provider usage 时记录输入/输出 token，缺失时记 `null` 而非 0。费用估算必须标注价格来源及时间，不得把估算当实际账单。

## 数据集分层与冻结

核心 Golden Set 为 **40 条人工审核的场景**，其中 24 条开发集、16 条冻结保留集。开发集可用于调试 Agent；保留集不用于 Prompt/工具定义迭代，正式报告单列保留集结果。每条场景有稳定 ID、版本、标签审核人、输入语义观测与时间、初始车辆状态、用户多轮消息、可用工具、期望工具序列与规范参数、期望最终状态、回答必须依据的事实、禁止虚构的事实，以及可接受的结果变体。金标不以某一个模型的输出反向生成。

另设 **80 条变体回归集**，从开发集的措辞、数值、缺失/过期状态和轮次组合扩展；它们不计入 40 条人工金标，也不作为最终保留集成绩。变体来源、生成规则和人工抽检记录均需保存。禁止在报告中把 `40 + 80` 称为 120 条独立人工金标。

### 40 条候选 Golden Set

| 分组 | 数量 | 开发集 ID | 冻结保留集 ID | 核心覆盖 |
|---|---:|---|---|---|
| 舱内状态理解 | 6 | C01–C04 | C05–C06 | 疲劳、正常、分心、在位、缺失观测、证据与状态区分 |
| 舱外道路理解 | 6 | R01–R04 | R05–R06 | 交通密度、车道、可行驶区、道路目标、道路数据有效性 |
| 舱内外联合判断 | 10 | X01–X06 | X07–X10 | 舱内、道路与车速/挡位的联合解释和缺失域隔离 |
| 车机工具编排 | 10 | T01–T06 | T07–T10 | 状态查询、空调、媒体、车窗、地点搜索与导航状态 |
| 多轮及不确定性 | 8 | M01–M04 | M05–M08 | 指代、确认、拒绝、改目标、工具失败和上下文更新 |

具体任务意图如下，实施时每条还必须填入结构化输入、期望事实与可接受结果，不以本表直接充当完整标注：

- C01 疲劳且高风险时询问驾驶状态；C02 正常且低风险时询问状态；C03 分心时询问驾驶表现；C04 驾驶员不在位时询问舱内情况；C05 眼睛观测为 `None` 时说明不确定性；C06 哈欠证据与高层状态不一致时仅报告已知事实。
- R01 中等交通密度时询问路况；R02 车道未检出时询问车道；R03 可行驶区域未检出时询问道路；R04 有行人/骑行者时询问周围目标；R05 有交通灯与标志时询问道路设施；R06 道路观测无效或过期时不陈述确定路况。
- X01 疲劳高风险、道路中等交通、车速 68 km/h 时询问是否该休息；X02 疲劳高风险但车辆已驻车时解释当前状态；X03 分心且车道未检出时同时提及两域；X04 舱内正常而车道未检出时聚焦道路；X05 分心且道路有行人时提供简短联合摘要；X06 驾驶员不在位且车辆驻车时不虚构驾驶员疲劳；X07 舱内过期、道路有效时只肯定道路事实；X08 道路过期、舱内高风险时只肯定舱内事实；X09 交通密度高且车速高时联合解释而不编造避障控制；X10 用户要求驾驶员、道路、车辆三域总览。
- T01 查询车辆状态；T02 查询空调状态；T03 请求设定舱温为 24°C；T04 请求开启空调；T05 请求播放指定音乐；T06 请求暂停音乐；T07 请求将音量设为指定数值；T08 查找附近服务区；T09 请求设置驾驶员车窗；T10 已导航时请求取消导航。每条按现有工具注册表确定可用工具、规范参数和最终状态，不期待不存在的控制能力。
- M01 查到服务区后说“就去这个”，应沿用工具返回的规范地点 ID；M02 查到服务区后明确拒绝；M03 查到服务区后改变目的地，不沿用旧目标；M04 待确认时给出模糊回复，记录是否正确澄清；M05 确认已过期时不误称导航完成；M06 工具返回失败后准确解释失败；M07 第二轮上下文从正常变疲劳后依据新状态回答；M08 调整温度后追问当前目标温度。

首轮 **8 条预检场景**仅从开发集选取 `C01、R02、X01、X03、T02、T03、T05、M01`，每模型先运行一次。它们要覆盖无工具问答、单工具、跨域事实和多轮工具。预检的通过门槛是两家客户端都能完成请求/工具调用、runner 能保存完整 trace、grader 能产出可解释判定；模型答错场景本身不阻止继续评估，应记录为失败案例。

## 评估执行与判定

每个 trial 创建新的 Agent、上下文、工具注册表和模拟车辆状态；相同场景按相同顺序注入语义观测，但在线模型自主选择工具与回复。工具使用现有本地模拟实现，不调用真实车辆。每个模型对 40 条金标各运行 3 次，合计 **240 个 case-trial**；一次 trial 可包含多个模型请求，必须另报实际请求数。两模型结果分开报告，不能把 240 个 trial 混成单一成功率。

运行器保存：case 版本/哈希、开发或保留集标记、provider、请求与响应模型、代码提交、解析后配置、工具 schema 哈希、trial 序号、时间线、工具请求/结果、最终上下文、回答、延迟、token usage（如可用）、错误类别及费用估算。网络超时、限流和模型空回复作为显式 trial 结果，不丢弃失败样本；重试次数有限并记录，避免无限费用与重复工具执行。输出数据按 run ID 隔离且不覆盖旧结果。

确定性 grader 负责期望工具选择、规范参数、工具顺序、最终状态、禁止动作和是否虚构“执行成功”。回答依据正确性使用人工写定的必要事实/禁止事实检查；无法机械判定的措辞标为 `needs_review`，由人工盲审，不让 Qwen 或 GLM 自评自己的结果。`needs_review` 不计为成功或失败，报告单列数量，直到完成判定才形成正式成功率。评估不读取隐藏思维链，也不要求模型暴露思维过程。

正式报告按模型、开发/保留集、任务分组分别给出分子/分母：端到端 Task Success、Tool Selection、规范参数 Exact Match、最终状态达成率、Context Grounding、三次全成功案例数、失败类型分布、p50/p95 延迟、实际请求数、token 与费用估算。每项均给出成功和失败实例链接；不在未执行前填写任何百分比。

## 阶段与验收

1. 先实现 provider 显式选择、统一 trial 记录、确定性 grader 和中文汇总报告；用假客户端跑完整离线测试，不依赖 API Key。
2. 对两家各做 API/工具预检，再跑 8 条开发集 pilot，审查 trace 与评分结果；若接口不兼容，先修框架再扩展数据集。
3. 补齐 40 条人工审核金标并冻结 16 条保留集；从开发集产生 80 条独立标识的变体回归集。
4. 两模型各 40 条 × 3 次，保存所有 trial、失败及成本证据；报告绝不把脚本化回放、变体集或感知小样本结果混入在线 Agent 指标。

本阶段不新增工具风险等级或 Prompt Injection 专项评测，但已有确认门禁与执行约束不得被绕过或删除。真实 API Key 仅从进程环境读取；`.env` 不提交，报告不含密钥、原始认证头或用户隐私数据。
