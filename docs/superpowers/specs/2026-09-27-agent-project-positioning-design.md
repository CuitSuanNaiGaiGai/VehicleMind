# VehicleMind 项目定位与面试叙事设计

## 状态

待用户审阅。本文只定义 GitHub 主页和面试讲述卡的叙事结构，不修改 Agent 实现。

## 目标读者与目标

面向招聘 Agent Engineer / AI 应用工程岗位的面试官，让读者在一分钟内理解：

1. VehicleMind 是什么系统。
2. 它针对哪类 Agent 工程问题。
3. 项目作者实现了哪些关键控制与评测机制。
4. 面试官可以从哪里运行和核对证据。

## 项目定位

**VehicleMind：基于 LangGraph 的多模态智能座舱 Agent 系统。**

系统将舱内外感知结果、车辆状态和用户请求整理为带质量信息的语义上下文，由 LangGraph `StateGraph` 管理 Agent 任务状态、事件路由、审批中断和恢复；VehicleAgent 处理有界模型/工具循环，ToolRegistry 负责执行时策略检查，PendingAction 表示待用户确认的敏感操作。结构化 trace 和 replay / evaluation 用于追踪流程及复核结果。

核心工程问题：怎样让 Agent 在多源且可能变化的座舱上下文中完成多步任务，同时为有副作用的工具调用提供明确授权、可恢复状态和可检查证据。

## 主页内容顺序

1. **标题与一句话定位**：明确完整项目名称，强调 LangGraph、多模态输入和 Agent 系统。
2. **问题与方案**：用疲劳驾驶后寻找服务区作为贯穿场景，简要展示上下文、风险响应、工具调用、用户审批、执行回读的因果链。
3. **演示入口**：突出可运行的离线演示，以及实际的模拟导航状态变化。
4. **Agent 工程重点**：集中说明四件事：StateGraph 任务编排、ToolRegistry / PendingAction 授权边界、有限恢复与重新确认、结构化 trace 与评测。
5. **架构图**：突出 Agent 控制流；舱内外感知、知识检索、行程记忆作为上下文来源或支持模块呈现。
6. **结果与证据**：主页保留少量代表性结果，并链接完整评测、失败案例和实现报告。现有评测失败记录及判定不得删除或改写成成功。
7. **快速开始与扩展模块**：保留可复现命令；感知算法、RAG、行程记忆等细节转为简短导航链接。

建议顶部介绍文案：

> VehicleMind 将舱内外感知结果、车辆状态与用户请求汇入统一语义上下文，并用 LangGraph 管理座舱 Agent 的任务状态、工具调用、人工审批和失败恢复。ToolRegistry 在执行边界校验敏感动作，结构化 trace 与回放评测把每条决策链关联到可核对的结果。

## 面试讲述卡内容顺序

1. 一句话定位和具体业务问题。
2. 端到端 Agent 执行链与模块职责。
3. 两项核心设计：LangGraph 管理流程状态；ToolRegistry / PendingAction 管理动作执行授权。
4. 一次可复核的真实工程故障及修复：`CONFIRMATION_REQUIRED` 被当成工具失败处理，导致误导回复或重复请求；修复后状态保持待确认。
5. 两类证据：确定性恢复场景，以及 Qwen / GLM 多次运行评测；数字指向现存报告。
6. 一段可直接口述的 60–90 秒项目介绍。

## 写作原则

- 让读者先看见 Agent 问题、系统设计和运行证据，再看技术组件列表。
- 用具体动作描述系统行为；“模拟导航”作为场景动作名称自然呈现。
- 不把技术栈数量当成项目贡献，不将支持模块提升为主线。
- 保留来源链接、失败报告、关键指标口径和已有技术文档，不伪造结果。
- README 和面试卡不重复铺陈大量边界说明；各报告中的方法、失败和口径细节保持原样。

## 验收标准

- README 标题清楚写出“基于 LangGraph 的多模态智能座舱 Agent 系统”。
- 首页首屏能直接回答项目解决的问题、Agent 的关键设计和可体验入口。
- 页面主线以 Agent Runtime、执行授权、恢复、Observability / Evaluation 为中心。
- 感知、RAG、记忆作为系统输入或支持能力出现，不与 Agent 主线争夺篇幅。
- 面试讲述卡形成连贯的 60–90 秒叙述，含一项工程故障复盘和可核验结果。
- 所有现存评测失败记录和原始报告链接保留；不产生未经证据支持的数字或能力声明。
- 现有快速开始命令与证据链接继续有效。
