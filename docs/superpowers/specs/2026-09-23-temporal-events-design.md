# Temporal Hazard Events Design

The existing detector emits `HIGH_RISK_DETECTED`, `LANE_LOST`, and `DRIVABLE_AREA_LOST` on a single semantic transition. Those alerts should instead require a sustained condition and obey a cooldown. Other informational transition events remain immediate.

Each hazard has a small independent gate: on first active observation it starts a timer; a later observation can emit only after the configured hold duration; the gate emits at most once per cooldown window while active. A clear or invalid observation resets the hold timer but retains the last emission time. A gap longer than the configured maximum also restarts the hold, because two distant samples do not prove continuity. Driver risk-change events use the same hold period; only the critical high-risk alert has a recurring cooldown. Lane and drivable-area loss gates become armed only after a positive observation, so startup defaults cannot count as a loss. The gate uses the runtime observation clock: replay passes `step.at_ms`, while live execution uses monotonic elapsed milliseconds. Source video timestamps are not mixed across services.

Timing parameters live in versioned `modules/config/events.yaml`, loaded and validated at detector construction. Demo defaults are 300 ms hold / 30 s cooldown for driver high risk and 500 ms hold / 10 s cooldown for each road loss, all with a 1000 ms maximum sample gap; these are showcase policy values, not validated safety thresholds. Replay observations carry synthetic processing latency zero and sequential metadata; invalid observations update quality and reset the relevant hazard gates without mutating semantics. The showcase replay adds a second high-risk observation after the hold interval so its event remains demonstrable. Tests cover one-frame suppression, sustained triggering, recovery, cooldown, startup defaults, invalid frames, long gaps, and deterministic replay.
